# VCPeer Live — build log, 2026-10-24 (round 2)

## Shipped: automatic VOD recording of every broadcast (Pro's second gated perk)

Backlog item 7 from the 2026-10-23 round. Every Pro broadcast is now
automatically recorded end-to-end and downloadable/playable afterward -
free plan gets nothing recorded, same "Pro adds X" pattern as team seats.

### How it works

- `control/src/lib/live.js` - `writeRecordFlag`/`removeRecordFlag` write
  (or delete) a `<ingestKey>.record` file in the shared volume, containing
  the broadcast id, every time `POST /api/live/go` runs - re-evaluated on
  EVERY go-live (not just the first), so a lapsed Pro subscription stops
  recording the very next broadcast, not on some separate cleanup pass.
  `listVodSegments`/`deleteVodSegments` read/remove the recorded files for
  one broadcast id from `<sharedDir>/vods/<ingestKey>/`.
- `mediamtx/scripts/fanout.sh` - if `<ingestKey>.record` exists when a
  stream goes live, starts a THIRD `ffmpeg -c copy` leg (alongside Owncast
  and the user's own destinations) that self-reads the just-published RTMP
  source into `vods/<ingestKey>/<broadcastId>.<segment>.mp4` instead of
  pushing it anywhere. A fresh segment file on every restart (startup race
  or mid-stream drop) so a transient failure can never truncate/corrupt
  bytes already on disk for that broadcast - same retry/backoff constants
  as the existing destination-push retry loop, reused rather than
  reinvented.
- `control/src/routes/vods.js` (new) - `GET /api/vods` (Pro-gated list,
  merges `listBroadcasts` history with on-disk segments so there's no
  separate VOD bookkeeping table), `GET /:broadcastId/segments/:segment/url`
  (mints a fresh signed URL), `DELETE /:broadcastId` (always allowed, even
  off Pro - reclaiming your own disk is reasonable regardless of plan).
  A SEPARATE, unauthenticated `GET /vods/:ingestKey/:broadcastId/:segment`
  streaming route (mounted at `/vods`, not `/api/vods`) serves the actual
  bytes with HTTP Range support, gated by a short-lived (15 min) HMAC
  token instead of a session cookie - works from a plain `<video>` tag or
  a shared link, same as any other VOD host.
- `control/src/lib/crypto.js` - `signVodToken`/`verifyVodToken`, HMAC-
  SHA256 reusing `ENCRYPTION_KEY` (no new secret to provision/rotate).
  Every path component (ingest key, broadcast id, segment) is validated
  against a strict regex BEFORE the token check even runs, so a malformed
  id can never reach `path.join`.
- `control/public/live.html`/`js/live.js` - new "Recordings" card: Pro
  sees past broadcasts with per-segment download/play links and a delete
  button; free sees an upsell message. Wired into `init()` and the
  post-checkout Pro-activation poll.

### Two real bugs found and fixed while verifying live (not theoretical)

Verified against a REAL docker-compose stack (owncast + mediamtx + control,
built fresh, not mocked) with a REAL `ffmpeg` RTMP publish into a REAL
MediaMTX ingest, not just unit tests:

1. **`-movflags +faststart` cannot survive the exact TERM-based stop this
   app already uses for every other ffmpeg leg.** First recording came out
   as a 48-byte unplayable file. Root cause: ffmpeg's SIGTERM handler
   aborts `av_write_trailer()` the same way it aborts the read loop, so a
   recording ended by `fanout-stop.sh`'s `kill` (the ONLY way a broadcast
   ever ends from this script's point of view) can never write the single
   trailer `+faststart` depends on. Fixed by switching to fragmented MP4
   (`+frag_keyframe+empty_moov+default_base_moof`) - a format with no
   trailer to lose, the same property that makes DASH/HLS segments
   crash-safe.
2. **Fragmented MP4 alone still wasn't enough.** A second real test still
   came out at 28 bytes - confirmed live (manual `ffmpeg` run inside the
   mediamtx container, watching the output file grow) that ffmpeg's own
   avio buffer was holding each finished fragment in memory rather than
   writing it to disk, so a kill between fragments still lost everything.
   Fixed with `-flush_packets 1`, forcing every fragment to hit disk as
   soon as it's muxed. Re-verified: `kill -TERM` mid-recording, then
   `ffmpeg -f null -i <file>` decoded the result with zero errors.

### Incidental fix

- `control/test/browser-go-live.test.js` - this round's extra `loadVods()`
  call in `live.js`'s `init()` IIFE extended how long that background
  chain keeps firing fetches after the test's own assertions already
  pass, making a PRE-EXISTING race in this test (it never awaits `init()`
  itself, just two fixed 50ms sleeps) fail about 1 run in 5: `server.
  close()` + `fs.rmSync(dataDir/sharedDir)` in the test's `finally` would
  sometimes run while `init()`'s tail was still mid-flight, crashing the
  whole test process with an unhandled `ENOENT`/`fetch failed` despite
  every assertion already having passed. Fixed by giving that background
  chain a 400ms grace period before teardown. Verified with 15 back-to-
  back runs (0 failures) and 7 full `npm test` runs (0 failures) after the
  fix, versus a reproducible ~1-in-5 failure rate before it.
