### 4. Debounced stream-health failure email alerts - done

- `control/src/lib/mailer.js` - refactored to share one
  `buildTransporter()` helper; added `sendStreamFailureEmail()`.
- `control/src/lib/healthAlerts.js` (new) - `checkFailuresAndNotify(data,
  {sharedDir, sendEmail})`: polls every live user's per-destination
  fan-out status (item 1's `.state` files), emails once per failure
  episode (debounced via a new `data.failureAlerts` store collection),
  clears the debounce on recovery OR when the broadcast ends, so a
  genuinely new failure in a later broadcast alerts again instead of
  being silenced forever.
- `control/src/server.js` - a `setInterval` (default 15s,
  `HEALTH_ALERT_INTERVAL_MS`) that runs the check independent of whether
  anyone has `/live` open in a browser tab - intentionally only started
  in the `require.main === module` block, never inside `createApp()`,
  so no background timer leaks into anything that imports the app.
- Verified: a standalone 5-pass simulation (send-once -> debounce ->
  recovery clears -> re-failure re-alerts -> broadcast-end clears) all
  produced the correct email-sent counts and alert-table states. Also
  booted the real server with a 500ms interval and confirmed no crash
  over several ticks with zero live users.

12. `store.js` concurrent-write hardening. Investigated: every current
    call site into `JsonStore.update()` is fully synchronous between its
    internal read and write (no `await` in between), so Node's
    single-threaded event loop cannot actually interleave two requests
    mid-update today - the real risk the backlog item names only
    materializes once a handler does async work (e.g. a mailer call)
    *between* a read and a dependent write. This round's new
    `healthAlerts.js` sidesteps it by reading, awaiting the email send,
    then doing one synchronous `store.update(() => data)` - never holding
    a stale read across an await. A real fix (in-process write-queue
    serialization, or the backlog's suggested `better-sqlite3` migration)
    is still worth doing before more async-handler features land, just
    not done this round.

### Code

- `control/src/lib/dodo.js` (new) - plain `fetch()`-based Dodo REST
  client (checkout session create, customer-portal link, Standard
  Webhooks HMAC-SHA256 verification with a 5-minute replay window) -
  ported from `~/products/bidstage-tenders/billing/dodo.ts`'s battle-
  tested pattern rather than adding the `dodopayments` SDK package for
  three call sites. `trustedDodoUrl()` only ever hands the browser a real
  `*.dodopayments.com` HTTPS URL.
- `control/src/lib/billing.js` (new) - pure, immutable plan/customer-id
  helpers on top of `data.users[].plan` (`getPlan`, `getBillingProfile`,
  `patchUserBilling`).
- `control/src/routes/billing.js` (new) - `GET /status`, `POST
  /checkout`, `POST /portal` (all auth-gated), plus
  `buildBillingWebhookHandler` mounted directly in `server.js` at `POST
  /api/billing/webhook` with `express.raw()` BEFORE the app-wide
  `express.json()` - signature verification needs Dodo's exact raw
  bytes, which `express.json()` would otherwise have already consumed.
  `applyWebhookEvent` resolves the target user by
  `metadata.vcpeer_live_user_id` (set at checkout) first, falls back to
  the already-stored `dodoCustomerId` for later events, and is a no-op
  for anything it can't resolve - never throws on an unrelated/stray
  event. Idempotent by construction (re-applying the same plan is a
  no-op), so no separate webhook-id dedupe table was needed for this
  state.
- `control/src/lib/team.js` (new) - the Pro-gated "multi-seat team access
  to one shared set of destinations" deliverable the same plan item
  named (didn't need items 7/9 built first, unlike the plan's other two
  listed Pro perks). `effectiveOwnerId(data, userId)` resolves whose
  destinations/ingest key/broadcast history a signed-in user acts on -
  checked LIVE against the owner's current plan on every call, not
  cached on the membership row, so a lapsed Pro subscription drops every
  team member back to their own (empty) account immediately, with no
  separate cleanup job. 3-seat cap, 7-day invite tokens, self-service
  leave.
- `control/src/routes/team.js` (new) - invite/accept/list/remove/leave,
  reusing `lib/mailer.js` (new `sendTeamInviteEmail`) the same way
  magic-link sign-in does.
- `control/src/routes/destinations.js`, `routes/live.js`,
  `routes/broadcasts.js` - swapped every `req.user.id` destinations/
  ingest-key/broadcast-history lookup for `effectiveOwnerId(data,
  req.user.id)`, so a team member transparently shares the owner's one
  ingest key, destination set and broadcast history instead of having
  their own empty one.
- `control/src/lib/store.js` - `_read()` now defaults any collection
  (`teamMembers`, `teamInvites`) a production `db.json` written before
  this round won't have yet, so this ships without a manual migration
  step on the box.
- `control/public/live.html` / `public/js/live.js` / `public/css/
  live.css` - new "Plan" card (Free/Pro badge, "Upgrade to Pro - $9/mo"
  -> real Dodo checkout redirect, "Manage billing" -> real Dodo customer
  portal) and "Team" card (owner: invite-by-email form + member/pending-
  invite list with remove/revoke; member: "you're on X's team" + leave).
  An invite link (`/live?acceptInvite=TOKEN`) stashes the token in
  `localStorage` before the inevitable 401-redirect-to-sign-in for a
  not-yet-signed-in invitee, then consumes it once they land back on
  `/live` signed in - no backend changes needed to the magic-link
  callback's redirect target.
